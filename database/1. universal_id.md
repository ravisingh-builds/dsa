# Universal ID

**Layman line:** A universal ID is a name two computers can mint on their own and still not collide.
**Working line:** A time-ordered ID keeps new rows on the hot edge of the index; a random ID scatters them.
**Staff line:** Sorted IDs help one B-tree and can burn one shard; the clock bits inside the ID are not `created_at`.

## Layman

An ID is the permanent name of a row, so you can find that row again.

A universal ID means each machine can create names by itself. The names still do not clash, and the machines do not have to share one counter.

Example: two ticket booths. If both start at 1, two people walk away with ticket 1. A universal ID is a name so wide that both booths can print without calling each other.

## Working engineer

Three common ways to name a row:

- **Auto-increment.** One database hands out 1, then 2, then 3. New rows land next to each other. A second database cannot hand out the same sequence unless the two of them share that counter.
- **Random UUID (version 4).** Almost all of the bits are random. Two machines will not collide in practice. New rows land in random places in the index.
- **Time-ordered ID (UUIDv7, and cousins such as ULID).** The front of the ID is the current time in milliseconds. An ID created later sorts after an ID created earlier, so new rows land near each other.

Why the landing spot matters: many databases keep the primary-key index in a **B-tree**, an ordered set of pages. A new sequential key goes into the newest page, which is already in memory. A random key opens some other page, and a full page has to split.

That is the usual case for MySQL/InnoDB, PostgreSQL, SQL Server, Oracle, and SQLite. InnoDB stores the row itself in primary-key order. PostgreSQL stores the row in a heap and keeps a separate B-tree for the primary key.

Some databases do not use a B-tree. Cassandra, ScyllaDB, and RocksDB use an **LSM tree**: they append sorted batches and merge them later. Key order still decides which batch a write falls into.

Example: a guestbook. Writing each name on the last line is one pen stroke. Writing each name on a random page means flipping around and sometimes tearing a full page in half.

## Staff engineer

### Uncoordinated names

The reason to use a universal ID is that many writers can insert without asking one counter first. A single auto-increment primary is a single writer and a cross-region hop. UUIDv7, a Snowflake-style ID, or a block of IDs checked out from the database each removes that hop in a different way.

Use auto-increment while one database owns the table. Move to a universal ID when more than one writer, region, or shard must mint IDs.

### Sorted on one machine, hot on a shard

On one B-tree, a time-ordered primary key is the cheaper insert: new keys share the rightmost page.

That same shape has a second failure once writes are huge or the data is split by key range. Every new key falls at the end of the range, so one page, one tablet, or one partition takes all the inserts. Google’s Bigtable guidance is the clear case: a timestamp or a rising counter as the start of the row key pins every write on one tablet. Spanner has the same hotspot with a monotonic key. InnoDB can hit it earlier, as latch contention on the single rightmost page.

A staff choice names both sides. Time-order the key when one database is the writer and index locality is the pain. Put a spread-out prefix in front (tenant, bucket, or a hash of a stable id) when the store splits by key range and one hot edge would take the write traffic.

### What sits inside a UUIDv7

The high bits are a 48-bit Unix time in milliseconds. That is why a byte-wise sort follows time. After that, the layout leaves room for a counter and for random bits. RFC 9562 allows those extra bits to act as a counter so that one generator, inside the same millisecond, still produces increasing IDs.

A common counter is 12 bits: 4096 IDs in one millisecond from one generator, on the order of 4 million per second. Past that, the generator has to do something explicit or the sort order breaks. Some libraries spend far more bits on the counter, and then rollover is not a realistic event for one process. Read the library. Do not memorize a bit diagram unless you are writing the library.

### Same millisecond

Inside one millisecond, the time prefix is identical. A counter is what makes one generator’s IDs increase. With no counter, those IDs differ only by random bits, so their order is arbitrary. Two generators in that same millisecond do not share a counter, so their IDs are not one global sequence.

### When the counter runs out

RFC 9562 requires the generator to handle rollover, or later IDs can sort before earlier ones. Two legal choices:

1. Freeze and wait until the clock reaches the next millisecond. The time bits stay honest. The caller can stall.
2. Move the timestamp one millisecond ahead of the real clock and start the counter over. IDs stay sorted. The time bits can sit in the future.

Libraries pick one. Some document it poorly. Check the one you ship before you depend on order under a burst.

### The ID is not `created_at`

Because of choice 2, and because clocks move, the time inside a UUIDv7 is a sort key. Store `created_at` from the clock you mean. Reading it back out of the ID will mark rows as created in the future whenever the generator was busy enough to step the timestamp forward.

### Order across machines

One process can keep its own IDs increasing. Two machines cannot, once their clocks disagree: the machine with the fast clock mints IDs that sort first even when its event happened later. ID order is not a “happened before” proof across servers.

When a design truly needs one global time order, that is a different tool. Spanner uses TrueTime and waits out the clock’s uncertainty. A UUIDv7 does not.

### What you ask before you adopt a library

Counter width. Rollover policy: wait, or step the timestamp forward. Monotonic inside one process, or also across processes on one host. Whether the database stores the 16 bytes in an order that matches that sort. Those four answers decide whether “UUIDv7” in a design doc is actually sorted.

### Other schemes, and the visible ID

- **Snowflake-style:** time, plus a worker number, plus a counter. Strong order per worker. Someone has to assign worker numbers, and the clock can still go backwards.
- **Blocks of IDs:** the database loans a range, and the app spends it locally. Ordered, and coordination happens only when the block runs out.
- **Two names:** a sequential primary key for the clustered index, and a random or time-ordered UUID as the id customers see. The index stays friendly, and outsiders cannot enumerate `…/orders/1`, `…/orders/2`.

A customer-visible UUIDv7 still leaks the creation time in its high bits. A sequential id leaks how many rows exist. Pick the leak you can accept, and keep the storage key matched to how the database splits writes.
